# 보스 레이드 부하 테스트

가상 사용자 500명이 보스 한 마리를 동시에 공격할 때 HP 갱신이 빠지지 않는지, 처치가 한 번만 일어나는지, 응답이 얼마나 걸리는지를 잰 기록이다. 목표는 [specs/006-raid/spec.md](../../specs/006-raid/spec.md)의 SC-001, SC-002, SC-003이고, 설계는 [research.md](../../specs/006-raid/research.md) R2, R3, R5, R15에 있다.

## 방법

```bash
MODE=sustain infra/k6/run-raid-load.sh     # 보스가 버티는 실행
MODE=defeat  infra/k6/run-raid-load.sh     # 보스가 중간에 처치되는 실행
```

- 스크립트가 HP가 정해진 보스를 새로 놓고, k6(`infra/k6/raid-attack.js`)가 회원 500명을 가입시킨 뒤 60초 동안 회원마다 1.05초에 한 번씩 공격한다. API를 직접 부른다(BFF를 거치지 않는다).
- 끝나고 5초 뒤에 받아들여진 응답(200) 수를 줄어든 HP, Redis의 기여 합, Postgres의 기여 합과 견준다. 처치 실행은 처치 기록과 알림 수도 본다.
- 쿨다운(1초)에 걸린 응답(429)과 보스가 끝난 뒤의 응답(409)은 받아들여지지 않은 것으로 센다. 둘 다 HP를 바꾸지 않아야 한다.

## 환경 (2026-10-09)

| 항목 | 값 |
|---|---|
| 기기 | Apple M1 Pro(8코어), 메모리 16GB, macOS |
| API | `apps/api`의 jar 하나(JDK 21, `e2e` 프로필), 호스트에서 실행 |
| DB, Redis | PostgreSQL 17, Redis 7.4. 같은 기기의 Docker 컨테이너 |
| 부하 | k6 v1.6.1, 같은 기기에서 실행 |
| 측정 중 부하 평균 | 10~14(코어 8개). 다른 작업이 함께 돌고 있었다 |

API, DB, Redis, k6가 한 기기에서 CPU를 나눠 썼다. 응답 시간은 이 조건에서의 값이고, 기기를 나누면 달라진다. 정확성(유실 0건, 처치 1건)은 조건과 상관없이 성립해야 하는 것이다.

## 결과

### 보스가 버티는 실행 (HP 1,000,000)

| 항목 | 값 |
|---|---|
| 받아들여진 공격(200) | 24,554건 |
| 쿨다운으로 거절(429) | 4,446건 |
| 그 밖의 실패 | 0건 |
| 줄어든 HP | 24,554 (1,000,000 → 975,446) |
| 기여의 합(Redis) | 24,554 (회원 500명) |
| 기여의 합(Postgres, 5초 뒤) | 24,554 |
| 공격 응답 시간 | 평균 128.5ms, p50 130.4ms, p95 232.8ms, p99 267.6ms, 최대 402.1ms |

- **SC-001 통과**: 받아들여진 공격 수, 줄어든 HP, 기여의 합(Redis와 Postgres)이 모두 같다. 유실 0건.
- **SC-003 통과**: p95 232.8ms로 목표(300ms) 안이다. 여유는 크지 않다.

### 보스가 중간에 처치되는 실행 (HP 10,000)

| 항목 | 값 |
|---|---|
| 받아들여진 공격(200) | 10,000건 |
| 쿨다운으로 거절(429) | 1,997건 |
| 보스가 끝난 뒤 거절(409) | 16,882건 |
| 그 밖의 실패 | 0건 |
| 줄어든 HP | 10,000 (10,000 → 0) |
| 기여의 합(Redis, Postgres) | 10,000, 10,000 |
| 보스 기록 | `DEFEATED`, HP 0, 참여자 500명 |
| 처치 알림 | 500건. 같은 회원에게 둘 이상 간 일 0건 |
| 공격 응답 시간 | 평균 110.2ms, p50 113.0ms, p95 184.8ms, p99 221.0ms, 최대 336.2ms |

- **SC-002 통과**: 받아들여진 공격이 보스의 HP와 정확히 같다. HP가 0 아래로 내려가지 않았고, 처치는 한 번 기록됐으며, 참여한 회원 500명에게 알림이 하나씩 갔다.

### 실시간 갱신 (SC-005)

가상 사용자 300명이 20초 동안 공격하는 사이, `topics=raid`로 붙은 스트림 하나가 받은 `raid` 이벤트를 초마다 셌다.

| 항목 | 값 |
|---|---|
| 초마다 받은 이벤트 | 1~2개 (가장 많은 초 2개) |
| 한 보스 안에서 HP | 줄어들기만 했다 |

- 상한(초당 네 번)을 넘지 않는다. 부하가 걸린 동안에는 내보내는 주기(250ms)가 Redis를 읽는 시간만큼 늘어져 초당 두 번쯤이 된다.
- 내보내는 일을 공용 스케줄러에서 전용 스레드로 옮기기 전에는 같은 조건에서 초당 한 번이었고 아무것도 오지 않는 초가 있었다. 옮긴 뒤로는 빈 초가 없다.

## 읽는 법

- 부하가 없을 때 공격 한 번은 10~40ms다. 500명 부하에서 평균이 130ms가 되는 것은 대부분 기다리는 시간이다.
- 공격 요청마다 세션이 살아 있는지를 Postgres에서 한 번 확인한다(M1의 설계). HP를 줄이는 Redis 스크립트보다 이 확인과 한 기기에 몰린 CPU가 응답 시간을 정했을 가능성이 크다. 프로파일링으로 확인한 것은 아니다.
- 운영의 무료 VM은 이 기기보다 느리다. 같은 부하를 운영에서 받으면 응답 시간은 더 길 것이다. 운영에는 부하를 걸지 않았다.
