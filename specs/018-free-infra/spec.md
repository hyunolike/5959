# Feature Specification: 무료 인프라로 이전

**Feature Branch**: `018-free-infra`

**Created**: 2026-11-09

**Status**: Draft

**Input**: User description: "무료 인프라로 이전: 월 인프라 비용 0원을 목표로 API를 Render 무료 웹 서비스(싱가포르, Docker, 512MB/0.1CPU, 15분 유휴 시 잠듦, 외부 keep-alive로 상시 유지), DB를 Neon 무료(싱가포르, pgvector, 월 100 CU-시간, 5분 유휴 시 scale-to-zero 강제)로 옮긴다. 전면 개편 허용. 필요한 변경: (1) GraalVM 네이티브 이미지 또는 JVM 경량화로 512MB 안에서 기동, (2) 1초~1분 주기로 DB를 폴링하는 @Scheduled 작업들을 이벤트 기반/저빈도로 바꿔 DB가 하루 10시간 이상 잠들게 함, keep-alive 헬스 체크는 DB를 건드리지 않음, (3) Redis 제거하고 단일 인스턴스 메모리 내 SSE 팬아웃, (4) Render 무료가 SMTP 587/465를 막으므로 비밀번호 재설정 메일을 HTTP API(Resend 등)로 발송, (5) 백업은 GitHub Actions에서 매일 pg_dump 후 R2 업로드, (6) 웹(Next.js)은 Cloud Run 무료 유지하되 아시아 리전 이전 검토, Artifact Registry 정리 정책, (7) 기존 GCP VM 데이터를 Neon으로 이전하고 GCP VM/고정 IP 제거. 수용 조건: 월 청구액 0원, Neon 월 CU-시간 100 이하, 실시간 알림과 예약 기능 동작 유지, 한국 사용자 응답 지연이 현재 이하."

## 배경

지금 운영 비용은 월 약 $18(2026-11-09 gcloud로 조회한 리소스에 공개 단가를 곱한 값)이다. 대부분이 미국 아이오와 리전의 VM(e2-small)과 고정 IP다. 원칙 VI("월 인프라 비용은 AI 사용료를 빼고 0원")를 어기고 있다. ADR-0004는 Oracle 무료 VM을 전제로 했지만 실제 배포는 GCP 유료 VM이 됐다.

옮길 곳(Render 무료 웹 서비스, Neon 무료 DB)의 제약이 기능의 모양을 바꾼다.

- 서버는 한 대뿐이고 메모리 512MB, CPU 0.1개다. 15분 동안 요청이 없으면 잠들고, 공급자가 언제든 재시작할 수 있다. 로컬 디스크는 재시작 때 사라진다. 메일 포트(465, 587)로 나가는 연결이 막혀 있다.
- DB는 5분 동안 요청이 없으면 잠들고 이를 끌 수 없다. 깨어 있는 시간이 한 달 100 CU-시간을 넘으면 그달 말까지 멈춘다. 가장 작은 크기로 계속 깨어 있으면 약 16일 만에 바닥난다.
- 지금 서버는 1초에서 1분 간격으로 DB를 조회하는 주기 작업이 열 개가 넘는다. 이대로 옮기면 DB가 잠들 틈이 없다.

## Clarifications

### Session 2026-11-09

- Q: 서버가 재시작될 때 레이드 공격을 최대 몇 초까지 잃어도 되는가? → A: 공격은 1초마다 묶어 기록하고, 정상 종료(배포, 공급자의 재시작) 때는 남은 공격을 모두 기록한 뒤 끝낸다. 프로세스가 갑자기 죽을 때만 직전 1초 안의 공격을 잃는다. 006 SC-006이 HP를 들고 있는 장치에 허용한 기준과 같다. (권장안으로 정함)
- Q: CPU가 0.1개인 새 서버에서 레이드 부하 목표를 어디까지 낮춰도 되는가? → A: 정확성(받아들인 공격 수 = 줄어든 HP = 기여의 합, 처치는 한 번)은 006처럼 가상 사용자 500명으로 시험한다. 응답 속도 목표는 50명 동시 공격에서 95%가 500ms 안으로 낮춘다. 006 SC-003(500명, 300ms)을 이 기준으로 바꾼다. (권장안으로 정함)
- Q: DB 사용량이 한도에 가까워지거나 백업이 실패했을 때 운영자 알림을 어디로 받는가? → A: 저장소 소유자의 메일로 받는다. 매일 도는 점검 작업 하나가 DB 사용량(깨어 있던 시간, 저장 용량)과 그날 백업을 확인하고, 문제가 있으면 실패로 끝나 GitHub의 실패 메일이 간다. 서버를 깨우는 요청이 실패하면 깨우기 서비스가 자체 메일로 알린다. 따로 가입하는 알림 서비스는 쓰지 않는다. (권장안으로 정함)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 회원은 이전 뒤에도 같은 서비스를 쓴다 (Priority: P1)

회원은 이전이 있었는지 몰라도 된다. 쓴 글, 댓글, 몬스터, 알림, 리포트가 그대로 있고, 로그인 방법도 그대로다. 한국에서 쓰는 회원에게 화면이 지금보다 늦게 뜨지 않는다.

**Why this priority**: 비용을 없애도 데이터를 잃거나 서비스가 느려지면 이전하는 의미가 없다.

**Independent Test**: 이전 전에 회원, 글, 댓글, 알림, 몬스터, 리포트의 수와 몇몇 회원의 화면을 기록해 두고, 이전 뒤 같은 회원으로 로그인해 같은 내용이 보이는지와 응답 시간을 잰다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 이전 전에 있던 회원일 때, **When** 이전 뒤 이메일, 카카오, 구글 가운데 쓰던 방법으로 로그인하면, **Then** 로그인되고 온보딩을 다시 하지 않는다.
2. **US1-AC2** **Given** 이전 전에 쓴 글과 댓글, 받은 알림, 처치한 몬스터, 주간 리포트가 있을 때, **When** 이전 뒤 피드, 마이페이지, 알림, 도감, 리포트를 열면, **Then** 이전 전과 같은 내용이 보인다.
3. **US1-AC3** **Given** 이전을 마쳤을 때, **When** 테이블마다 행 수를 이전 전 기록과 견주면, **Then** 모두 같다.
4. **US1-AC4** **Given** 서비스가 깨어 있을 때, **When** 한국에서 피드를 열면, **Then** 응답 시간이 이전 전 측정값보다 길지 않다.
5. **US1-AC5** **Given** DB가 잠들어 있을 때, **When** 한국에서 피드를 열면, **Then** 3초 안에 피드가 보인다. 오류 화면이 나오지 않는다.
6. **US1-AC6** **Given** 이전하는 동안일 때, **When** 회원이 서비스를 열면, **Then** 점검 중이라는 안내를 본다. 쓰기 요청이 조용히 사라지지 않는다.

### User Story 2 - 운영자는 월 0원으로 운영한다 (Priority: P1)

저장소 소유자는 매달 청구서를 보지 않아도 된다. 서비스를 돌리는 데 드는 인프라 비용이 0원이고(AI 사용료는 따로), 무료 한도에 가까워지면 미리 안다.

**Why this priority**: 이 기능을 만드는 까닭이다. 원칙 VI를 다시 지키게 된다.

**Independent Test**: 이전을 마치고 한 달 동안 운영한 뒤, 모든 공급자의 청구액과 DB가 깨어 있던 시간을 본다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 이전 뒤 한 달이 지났을 때, **When** 모든 공급자의 청구서를 보면, **Then** AI 사용료를 뺀 금액이 0원이다.
2. **US2-AC2** **Given** 평소만큼 쓰인 한 달일 때, **When** DB가 깨어 있던 사용량을 보면, **Then** 무료 한도의 80%를 넘지 않는다.
3. **US2-AC3** **Given** 아무도 쓰지 않는 시간일 때, **When** 서버가 깨어 있는지 확인하는 요청만 오면, **Then** DB는 깨지 않는다.
4. **US2-AC4** **Given** 그달 DB 사용량이 무료 한도의 70%를 넘었을 때, **When** 그날의 점검이 돌면, **Then** 운영자가 메일로 알림을 받는다.
5. **US2-AC5** **Given** 회원이 15분 넘게 아무 요청을 하지 않았을 때, **When** 다음 요청이 오면, **Then** 서버가 잠들어 있지 않아 바로 응답한다.
6. **US2-AC6** **Given** 이전을 마쳤을 때, **When** 옛 GCP 프로젝트의 리소스를 보면, **Then** VM, 디스크, 고정 IP가 없고 남은 리소스는 무료 한도 안이다.

### User Story 3 - 실시간 알림과 레이드는 서버 한 대에서 그대로 동작한다 (Priority: P1)

회원은 댓글과 공감 알림을 실시간으로 받고, 레이드 보스를 함께 공격하며 HP가 줄어드는 것을 실시간으로 본다. 지금은 서버끼리 신호를 주고받는 저장소가 따로 있지만, 이전 뒤에는 서버가 한 대라 그 저장소 없이 같은 동작을 한다.

**Why this priority**: 실시간 알림과 레이드는 이미 내보낸 기능이다. 이전 때문에 빠지면 회원이 바로 알아챈다.

**Independent Test**: 회원 둘이 같은 글을 연 채 한 사람이 댓글을 달아 다른 사람에게 알림이 오는지, 여럿이 레이드 보스를 동시에 공격해 HP와 기여가 맞는지 본다. 서버를 재시작한 뒤에도 본다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 회원 A가 알림 연결을 열어 두었을 때, **When** 회원 B가 A의 글에 댓글을 달면, **Then** A에게 5초 안에 알림이 온다.
2. **US3-AC2** **Given** 알림 연결이 끊겼다가 다시 붙었을 때, **When** 끊긴 동안 알림이 생겼으면, **Then** 빠짐없이 순서대로 받는다.
3. **US3-AC3** **Given** 여러 회원이 같은 보스를 동시에 공격할 때, **When** 공격이 끝나면, **Then** 받아들인 공격 수와 줄어든 HP와 기여의 합이 같다.
4. **US3-AC4** **Given** 레이드 화면을 연 회원이 있을 때, **When** 다른 회원이 공격하면, **Then** 1초 안에 HP가 바뀐 것을 본다.
5. **US3-AC5** **Given** 레이드 중에 서버가 정상 종료로 재시작됐을 때, **When** 다시 뜨면, **Then** 받아들인 공격이 하나도 사라지지 않고 보스의 HP와 기여가 재시작 전과 같으며, 회원은 다시 공격할 수 있다.
6. **US3-AC8** **Given** 레이드 중에 서버 프로세스가 갑자기 죽었을 때, **When** 다시 뜨면, **Then** 사라진 공격은 죽기 직전 1초 안의 것뿐이고, 사라진 공격은 HP와 기여 양쪽에서 함께 빠져 숫자가 서로 맞는다.
7. **US3-AC6** **Given** 서버가 재시작될 때, **When** 알림 연결이 끊기면, **Then** 웹이 다시 붙고 회원은 오류 화면을 보지 않는다.
8. **US3-AC7** **Given** 회원이 비밀번호를 바꾸거나 탈퇴했을 때, **When** 그 회원의 알림 연결이 열려 있으면, **Then** 연결이 닫힌다.

### User Story 4 - 뒤에서 도는 일은 DB를 계속 깨우지 않고 제때 끝난다 (Priority: P1)

감정 분석, 위험 분류, 임베딩, AI 친구의 반응과 글쓰기, 주간 리포트와 편지, 레이드 보스 교체, 오래된 기록 정리는 지금처럼 동작한다. 다만 할 일이 없을 때 DB에 계속 묻지 않는다. 할 일이 생겼을 때나 정해진 때에만 깨운다.

**Why this priority**: 이 부분을 바꾸지 않으면 DB 한도가 보름 만에 바닥나 서비스 전체가 멈춘다(US2가 성립하지 않는다).

**Independent Test**: 새 글 하나를 쓰고 감정 분석, 몬스터, 위험 분류, 임베딩, AI 친구의 반응이 지금과 같은 시간 안에 생기는지 본다. 그 뒤 아무도 쓰지 않는 상태로 두고 DB가 잠드는지 본다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 새 글이 올라왔을 때, **When** AI가 정상이면, **Then** 감정 분석과 몬스터는 지금처럼 1분 안에 생긴다.
2. **US4-AC2** **Given** AI 호출이 실패했을 때, **When** 다시 시도할 때가 되면, **Then** 지금의 재시도 일정(30초부터 두 배씩, 최대 5분, 24시간 뒤 포기)대로 다시 시도한다.
3. **US4-AC3** **Given** 재시도할 일도, 기다리는 AI 친구 반응도, 정해진 작업도 없을 때, **When** 마지막 요청 뒤 10분이 지나면, **Then** DB가 잠들어 있다.
4. **US4-AC4** **Given** 기다리는 일이 있는 채 서버가 재시작됐을 때, **When** 다시 뜨면, **Then** 기다리던 일을 잃지 않고 제때 이어서 한다.
5. **US4-AC5** **Given** 지난주에 글을 쓴 회원이 있을 때, **When** 월요일이 되면, **Then** 지금처럼 그날 안에 주간 리포트와 알림을 받는다.
6. **US4-AC6** **Given** 하루가 지났을 때, **When** 정리 작업 결과를 보면, **Then** 지금과 같은 기준(알림 90일, 이벤트 발행 7일, 안전 기록 1년 등)으로 지워져 있다.
7. **US4-AC7** **Given** 글이 없는 조용한 시간이 6시간을 넘었을 때, **When** AI 친구 글쓰기가 켜져 있으면, **Then** 지금처럼 AI 친구가 글을 쓴다.
8. **US4-AC8** **Given** 레이드 보스가 물러날 때가 됐을 때, **When** 그때가 되면, **Then** 지금처럼 1분 안에 다음 보스로 바뀐다.

### User Story 5 - 비밀번호 재설정 메일은 막힌 포트 없이 간다 (Priority: P2)

비밀번호 재설정(015)은 메일 포트(587)로 보내게 설정되어 있는데, 옮길 서버는 465와 587을 막는다. 막히지 않은 포트로 보내고, 그것도 막히면 메일 발송 서비스의 웹 API로 바꾼다. 회원이 보는 흐름은 015 그대로다.

**Why this priority**: 015는 꺼진 채로 나가 있어 이전 첫날 깨지는 것은 없다. 켜려면 필요하다.

**Independent Test**: 메일 발송을 켜고 이메일 가입 회원으로 재설정을 요청해 메일이 오는지, 링크로 비밀번호를 바꿀 수 있는지 본다.

**Acceptance Scenarios**:

1. **US5-AC1** **Given** 메일 발송이 켜져 있을 때, **When** 이메일 가입 회원이 재설정을 요청하면, **Then** 1분 안에 메일이 온다.
2. **US5-AC2** **Given** 메일 발송 서비스가 잠깐 실패했을 때, **When** 다시 시도할 때가 되면, **Then** 015와 같은 기준으로 다시 보내고 한 시간이 지난 요청은 보내지 않는다.
3. **US5-AC3** **Given** 015의 인수 조건 전체일 때, **When** 바뀐 발송 방식으로 다시 확인하면, **Then** 모두 통과한다.

---

### User Story 6 - 데이터는 매일 백업되고 복구할 수 있다 (Priority: P2)

DB를 남의 서비스에 두더라도 데이터를 잃지 않게 매일 백업을 받고, 백업으로 실제로 되살려 본다.

**Why this priority**: 무료 DB는 스냅숏을 하나만 남긴다. 사고가 나면 백업이 전부다.

**Independent Test**: 백업 작업을 돌린 뒤 빈 DB에 그 백업을 되살려 행 수를 견준다.

**Acceptance Scenarios**:

1. **US6-AC1** **Given** 하루가 지났을 때, **When** 백업 보관소를 보면, **Then** 그날의 백업이 있고 14일보다 오래된 백업은 없다.
2. **US6-AC2** **Given** 가장 최근 백업이 있을 때, **When** 복구 절차대로 빈 DB에 되살리면, **Then** 테이블마다 행 수가 백업 시점과 같고 서버가 그 DB로 뜬다.
3. **US6-AC3** **Given** 백업이 실패했을 때, **When** 실패하면, **Then** 운영자가 알림을 받는다.
4. **US6-AC4** **Given** 백업이 도는 시간일 때, **When** 백업이 끝나면, **Then** 그 때문에 DB가 깨어 있던 시간은 하루 10분을 넘지 않는다.

### User Story 7 - 옛 인프라를 정리한다 (Priority: P3)

이전이 끝나고 새 환경이 안정되면, 돈이 나가던 옛 VM과 고정 IP를 지우고 쌓여 있던 이미지를 정리한다. 남은 것은 무료 한도 안에 있다.

**Why this priority**: 이전이 끝나야 할 수 있고, 지우는 일이라 되돌릴 수 없다.

**Independent Test**: 정리 뒤 옛 프로젝트의 리소스 목록과 다음 달 청구액을 본다.

**Acceptance Scenarios**:

1. **US7-AC1** **Given** 새 환경으로 7일 동안 문제없이 운영했을 때, **When** 옛 VM을 지우기 전에, **Then** 옛 DB의 마지막 백업을 따로 보관해 둔다.
2. **US7-AC2** **Given** 정리를 마쳤을 때, **When** 옛 프로젝트의 리소스를 보면, **Then** VM, 디스크, 고정 IP가 없다.
3. **US7-AC3** **Given** 웹 이미지 저장소일 때, **When** 새 이미지가 올라가면, **Then** 최근 몇 개만 남고 저장 용량이 무료 한도 안에 있다.

### Edge Cases

- **DB 한도를 다 쓴 달**: 그달 말까지 DB가 멈춘다. 70%에서 알림을 받고(US2-AC4), 그래도 넘으면 서버는 죽지 않고 "잠시 쓸 수 없다"는 안내를 준다(503 `DATABASE_UNAVAILABLE`, FR-025). 운영자가 할 일은 quickstart에 적는다.
- **공급자가 서버를 아무 때나 재시작할 때**: 메모리에만 있던 것(알림 연결, 레이드의 최신 값, 다음 할 일의 시각)이 사라진다. 다시 뜰 때 DB에서 한 번 읽어 되살린다. 공급자의 재시작은 종료 신호를 먼저 보내므로 레이드 공격을 잃지 않는다(US3-AC5). 프로세스가 갑자기 죽을 때만 직전 1초를 잃는다(US3-AC8). 이것은 006 SC-006의 "API 서버를 다시 띄워도 사라지지 않는다"를 이 기준으로 바꾼다.
- **서버를 깨우는 외부 요청이 멈출 때**: 15분 뒤 서버가 잠들고, 다음 요청은 서버가 뜰 때까지 기다린다. 그동안 예약 작업도 멈춘다. 깨어나면 밀린 일을 이어서 한다(US4-AC4). 깨우는 요청이 멈추면 운영자가 안다.
- **DB가 잠든 사이 첫 요청**: DB가 깨어나는 동안 응답이 늦다. 3초 안에 답한다(US1-AC5).
- **배포 중**: 서버가 한 대라 새 버전이 뜨는 동안 잠깐 끊길 수 있다. 알림 연결은 웹이 다시 붙는다.
- **사람이 많이 몰리는 레이드**: CPU가 0.1개라 지금보다 처리량이 낮다. 500명이 몰려도 숫자는 맞아야 하고 응답이 느려지는 것은 받아들인다. 속도 목표는 50명 기준이다(SC-010).
- **임베딩의 크기**: 글이 늘면 DB 저장 용량(1GB)에 가까워진다. 용량도 한도 알림에 넣는다.
- **이전 도중 실패**: 옛 환경을 지우기 전이라 되돌릴 수 있다. 되돌리는 절차를 미리 적어 둔다.

## Requirements *(mandatory)*

### Functional Requirements

**이전과 데이터**

- **FR-001**: 이전은 모든 테이블의 모든 행을 옮겨야 한다. 이전 뒤 테이블마다 행 수가 이전 전과 같아야 한다.
- **FR-002**: 이전하는 동안 쓰기 요청을 받지 않고 점검 안내를 보여야 한다. 점검 시간은 1시간 안이어야 한다.
- **FR-003**: 이전이 실패하면 옛 환경으로 되돌릴 수 있어야 한다. 옛 환경은 새 환경이 7일 동안 안정된 뒤에만 지운다.
- **FR-004**: 로그인 상태, 비밀 값, 외부 로그인 설정(카카오, 구글의 돌아올 주소)이 새 주소에서 동작해야 한다.

**비용과 한도**

- **FR-005**: 서비스를 돌리는 인프라는 모두 무료 플랜 안에 있어야 한다. AI 사용료만 예외다.
- **FR-006**: 서버가 깨어 있는지 확인하는 요청은 DB에 닿지 않아야 한다.
- **FR-007**: 할 일이 없을 때 서버는 DB에 묻지 않아야 한다. 다음에 할 일의 시각을 알고 있다가 그때만 DB를 깨운다.
- **FR-008**: 하루에 한 번 도는 정리 작업은 한 번 깨울 때 함께 돌아야 한다.
- **FR-009**: DB 사용량(깨어 있던 시간, 저장 용량)이 그달 무료 한도의 70%를 넘으면 운영자에게 메일로 알려야 한다. 사용량은 하루 한 번 점검한다.
- **FR-010**: 서버는 메모리 한도(512MB) 안에서 떠야 하고, 평소 부하에서 메모리 부족으로 죽지 않아야 한다.
- **FR-025**: DB에 연결할 수 없으면 서버는 죽지 않고 그 요청에 503과 "잠시 쓸 수 없다"는 안내를 준다. DB를 보지 않는 헬스 체크는 계속 UP이다.
- **FR-011**: 서버가 잠들지 않도록 외부에서 주기적으로 깨워야 한다. 깨우는 요청이 실패하면 운영자가 메일로 알아야 한다.

**실시간과 레이드**

- **FR-012**: 실시간 알림은 서버끼리 신호를 주고받는 저장소 없이 서버 안에서 전달해야 한다. 알림을 보낼 것은 지금처럼 DB의 번호로 정한다.
- **FR-013**: 레이드의 공격 판정(쿨다운, HP, 기여, 처치)은 지금처럼 한 번에 함께 바뀌어야 한다. 서버 한 대 안에서 겹친 공격이 서로 끼어들지 않아야 한다.
- **FR-014**: 레이드의 기록은 공격이 있을 때만, 1초마다 묶어 DB에 적어야 한다. 정상 종료 신호를 받으면 남은 공격을 모두 적은 뒤 끝낸다. 서버가 다시 뜨면 기록에서 보스의 상태를 다시 세워야 한다.
- **FR-015**: 레이드를 쓸 수 없는 동안에도 다른 기능에는 번지지 않아야 한다(006의 동작 유지).

**뒤에서 도는 일**

- **FR-016**: 감정 분석, 위험 분류, 임베딩, 주간 편지, AI 친구 반응의 재시도 일정과 포기 기준은 지금과 같아야 한다.
- **FR-017**: 서버가 다시 뜰 때 기다리던 일의 다음 시각을 DB에서 한 번에 읽어 이어서 해야 한다.
- **FR-018**: 주간 리포트, 정리 작업, AI 친구 글쓰기, 레이드 보스 교체는 지금과 같은 때에 돌아야 한다.

**메일**

- **FR-019**: 재설정 메일은 옮길 서버가 막지 않는 포트로 보내야 한다. 발송 서비스가 그 포트를 받지 않으면 발송 서비스의 웹 API로 보낸다. 015의 동작(켜고 끄기, 재시도, 한 시간 기한, 가입 여부를 숨기는 응답)은 그대로다.

**백업과 정리**

- **FR-020**: DB를 매일 백업해 서버와 다른 곳에 14일 동안 보관해야 한다. 실패하면 운영자에게 메일로 알린다.
- **FR-021**: 복구 절차를 새 환경에 맞게 고쳐 적고, 이전을 마치기 전에 한 번 실제로 되살려 봐야 한다.
- **FR-022**: 웹 이미지 저장소는 최근 이미지 몇 개만 남겨 무료 한도 안에 있어야 한다.
- **FR-023**: 옛 VM, 디스크, 고정 IP를 지워야 한다. 지우기 전에 옛 DB의 마지막 백업을 따로 보관한다.
- **FR-024**: ADR-0004를 대체하는 새 ADR에 DB와 서버를 어디에 두는지와 그 까닭을 적어야 한다.

### Key Entities

- **다음 할 일의 시각**: 재시도, AI 친구 반응, 주간 작업 가운데 가장 이른 다음 시각. 서버 메모리에 있고, 재시작하면 DB에서 다시 계산한다. 새로 저장하지 않는다.
- **레이드 보스의 실시간 상태**: 살아 있는 보스의 HP, 회원별 기여와 쿨다운. 지금은 별도 저장소에 있고 이전 뒤에는 서버 메모리에 있다. DB의 기록이 재시작 때의 기준이다.
- **사용량 지표**: 그달 DB가 깨어 있던 시간과 저장 용량. 공급자에서 읽어 한도와 견준다.
- **백업**: 하루 하나, 14일 보관.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 옛 인프라를 정리한 다음 달부터 인프라 청구액이 AI 사용료를 빼고 0원이다. 되돌릴 수 있게 옛 VM을 남겨 두는 7일 동안의 비용(약 $4)은 예외다.
- **SC-002**: 평소 사용량의 한 달 동안 DB가 깨어 있던 사용량이 무료 한도의 80% 이하다.
- **SC-003**: 아무도 쓰지 않는 시간에는 마지막 요청 뒤 10분 안에 DB가 잠든다.
- **SC-004**: 한국에서 잰 피드 응답 시간의 95%가 이전 전 측정값 이하다. DB가 잠들어 있었던 첫 요청도 3초 안에 답한다.
- **SC-005**: 이전 뒤 테이블마다 행 수가 이전 전과 같고, 회원이 데이터를 잃었다는 신고가 없다.
- **SC-006**: 실시간 알림의 99%가 5초 안에 도착하고, 레이드 공격 수와 HP와 기여의 합이 언제나 같다. 가상 사용자 500명이 동시에 공격해도 같고, 처치는 한 번만 기록된다.
- **SC-007**: 지금 있는 자동 테스트와 e2e가 모두 통과한다(Redis에 기대던 테스트는 새 동작을 보는 테스트로 바뀐다).
- **SC-008**: 점검 시간이 1시간 안이다.
- **SC-009**: 백업에서 빈 DB로 되살리는 데 30분이 넘지 않는다.
- **SC-010**: 회원 50명이 동시에 레이드 보스를 공격할 때 공격 요청의 95%가 500ms 안에 응답을 받는다. 측정한 값을 문서에 남긴다.

## Assumptions

- 사용자가 2026-11-09에 "시스템 전면 개편해도 된다"고 했다. 서버의 실행 방식, 실시간 신호, 레이드의 저장 위치, 주기 작업의 구조를 바꿔도 된다. 회원이 보는 기능과 데이터는 바꾸지 않는다.
- 서버와 DB는 싱가포르에 둔다. 둘 다 한국에서 가장 가까운 무료 리전이다(Render, Neon 모두 서울이나 도쿄가 없다). 지금의 미국 아이오와보다 한국에서 가깝다.
- 웹은 지금의 무료 플랜을 그대로 쓰고, 서버와 가까운 아시아 리전으로 옮길지는 plan 단계에서 응답 시간을 재서 정한다.
- 서버를 실행하는 방식(네이티브 실행 파일이냐 가벼운 설정의 JVM이냐)은 plan 단계에서 메모리와 기동 시간을 재서 정한다.
- 지금 DB는 무료 저장 한도(1GB)보다 훨씬 작다. 백업 버킷 전체가 6MB 미만이다.
- Render 무료 플랜의 월 750시간은 서버 한 대를 한 달 내내 켜 두기에 충분하다. 같은 작업 공간에 다른 무료 서비스를 두지 않는다.
- 서버를 깨우는 요청을 보내는 것은 Render 무료 문서에서 금지하지 않는다(2026-11-09 확인).
- 계정 가입(Render, Neon, 메일 발송 서비스, 백업 보관소)과 비밀 값 입력은 저장소 소유자가 한다.
- 무료 플랜의 조건은 공급자가 바꿀 수 있다. 2026-11-09에 공식 문서에서 확인한 값을 기준으로 한다.
- 메일 발송은 015처럼 꺼진 채로 나간다. 켜는 것은 이 기능의 범위 밖이다.
