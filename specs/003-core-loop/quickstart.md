# Quickstart: 핵심 루프 검증 (003-core-loop)

구현이 끝난 뒤 기능이 처음부터 끝까지 동작하는지 확인하는 절차다. 계약은 [contracts/core-loop.openapi.yaml](contracts/core-loop.openapi.yaml)(구현 후에는 저장소 루트 `contracts/openapi.yaml`), 데이터는 [data-model.md](data-model.md)를 본다.

## 준비

```bash
# API: e2e 프로필은 가짜 감정 분석기를 쓴다(research R3)
cd apps/api && SPRING_PROFILES_ACTIVE=local,e2e ./gradlew bootRun
# Docker 이미지를 빌드할 수 없으면: ./gradlew bootJar 뒤 JDK 21로 java -jar build/libs/api.jar
# (SPRING_PROFILES_ACTIVE=e2e, DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET, OGU_BFF_KEY를 넘긴다)

# 웹
API_ORIGIN=http://localhost:8080 BFF_API_KEY=local-bff-key APP_ORIGIN=http://localhost:3000 \
  pnpm --filter web dev
```

가짜 분석기 규칙: 본문이 `[불안:높음]`처럼 시작하면 그 감정과 강도를, `[실패]`로 시작하면 항상 예외를, `[실패:N]`으로 시작하면 처음 N번만 예외를 던지고 그다음에는 본문 길이로 정한 값을 돌려준다. 그 밖에는 본문 길이로 정한 값을 돌려준다.

## 자동 검증

```bash
cd apps/api && ./gradlew test        # 모듈, 통합, 계약, 동시성 테스트

```

## 성능 측정

2026-10-05에 로컬에서 쟀다(T058). Docker 이미지 빌드가 이 기기에서 멈추므로 API는 호스트에서 jar(`java -jar build/libs/api.jar`, JDK 21, `e2e` 프로필)로 띄우고, DB는 따로 띄운 `pgvector/pgvector:pg17` 컨테이너를 썼다. 웹은 `pnpm build && pnpm start`(APP_ENV=e2e)다. 기기는 8코어 Mac이고, 같은 기기에서 다른 세션의 빌드와 테스트가 함께 돌아 부하(load average, 1분/5분/15분)가 30~90으로 매우 높았다. 아래 수치는 이 부하를 그대로 받은 값이라 실제 서버보다 나쁘게 나온 쪽으로 봐야 한다.

### 피드와 공감 API (SC-003, plan 성능 목표)

글 10,025개(시드 1만 개는 직군 9개와 경력 8개 스냅숏을 고르게 섞고 공감 수 0~199, 모두 분석 완료와 몬스터 포함)를 넣고, API(`/api/v1/*`)를 한 회원 토큰으로 차례로 100번씩 불렀다. 데우기 5번은 뺐다. 단위는 ms다.

### 피드 스크롤 끊김 (SC-005)

Playwright Chromium에 CDP로 `Emulation.setCPUThrottlingRate`를 4로 걸고 Pixel 7 에뮬레이션(뷰포트 412×839, 배율 2.625, 모바일, 터치)로 `/home`을 열었다. 600px 휠 스크롤을 40ms마다 60번 보내 빠르게 내리는 동안 `requestAnimationFrame` 시각을 모두 기록했다. 프레임 간격을 16.7ms로 나눠 반올림한 값에서 1을 뺀 것을 끊긴 프레임으로 세고, 비율은 끊긴 프레임 / (그린 프레임 + 끊긴 프레임)이다. 피드는 스크롤하며 다음 쪽을 계속 불러왔다.

| 회차 | 시간(ms) | 그린 프레임 | 끊긴 프레임 | 끊긴 비율 | 50ms 넘는 프레임 | 가장 긴 프레임(ms) | 불러온 글 | 부하 |
|---|---|---|---|---|---|---|---|---|
| 1 | 4400 | 241 | 24 | 9.1% | 5 | 83 | 140 | 44.2 → 41.9 |
| 2 | 3733 | 220 | 5 | 2.2% | 1 | 67 | 160 | 41.9 → 40.6 |
| 3 | 3933 | 236 | 1 | 0.4% | 0 | 33 | 160 | 40.6 → 37.6 |

첫 회차는 다음 쪽 응답과 정지 이미지 디코딩이 처음 들어오는 구간이라 끊김이 몰렸고, 같은 목록을 다시 내린 2, 3회차는 거의 끊기지 않았다. 실제 중급 휴대폰이 아니라 데스크톱 CPU를 4배 늦춘 근사치다.

### 몬스터가 나타나기까지 (SC-001)

이 기기에는 실제 감정 분석 키(`AI_API_KEY`)가 없어 실제 엔드포인트로는 재지 못했다. 대신 `e2e` 프로필의 가짜 분석기로 같은 경로(글 저장, 커밋 뒤 비동기 분석, `EmotionAnalyzed`, 몬스터 생성)를 지나는 시간을 쟀다. 글 20개를 차례로 쓰고, 201 응답 직전부터 상세 조회에 몬스터가 보일 때까지 100ms 간격으로 확인했다. LLM 호출 시간은 들어 있지 않으므로 실제 값은 여기에 공급자 응답 시간을 더해야 한다.

| 분석기 | 글 | p50 | p95 | 최대 | 30초 안 | 부하 |
|---|---|---|---|---|---|---|
| 가짜 분석기(대용) | 20 | 347ms | 1083ms | 1144ms | 20/20 | 62.1 → 86.6 |

## 수동 시나리오 실행 기록

2026-10-05에 위 환경에서 12개를 모두 끝까지 돌렸다(T059). 시나리오 3~11은 API를 직접 부르는 스크립트로, 1, 2, 12는 Playwright로 실제 웹 화면에서 확인했다. 회원 A, B, C, D는 스크립트가 가입과 온보딩까지 마쳤다.

| # | 결과 | 확인한 내용 |
|---|---|---|
| 1 | 통과 | 글쓰기 화면에서 올리면 `/post/{id}`로 가고 "분석 중"이 보인다. 가짜 분석기가 2초 안에 끝나 처음 한 번은 "분석 중"을 보기 전에 몬스터가 떠서 놓쳤고, 다시 돌린 회차와 첫 시도가 실패하는 글(`[실패:1]`)에서 모두 확인했다 |
| 2 | 통과 | 새로고침 없이(navigation 1번) 불안 몬스터 HP 10/10, 상세에 3D 캔버스 |
| 3 | 통과 | 자기 글 공감은 403 `CANNOT_LIKE_OWN_POST`, 자기 댓글은 201, HP 10 그대로 |
| 4 | 통과 | HP 10 → 9 → 6, 두 번째 댓글 뒤에도 6 |
| 5 | 통과 | HP 6 → 5 → 2 |
| 6 | 통과 | 답글이 원 댓글의 `replies`에 들어가고 HP 2 그대로 |
| 7 | 통과 | 공감 수 1 → 0 → 1, HP 2 그대로 |
| 8 | 통과 | HP 2 → 1 → 0, 몬스터 `DEFEATED` |
| 9 | 통과 | `[실패:2]` 글은 분석 중, 몬스터 없음, 공감 수 2 |
| 10 | 통과 | 작성 뒤 100초에 몬스터가 생기고 HP 8/10(공감 2 소급 반영) |
| 11 | 통과 | 인기순은 공감 수 내림차순, 개발 3년차 필터는 그 프로필의 글만 |
| 12 | 통과 | 움직임 줄이기를 켜면 캔버스가 사라지고 "불안 몬스터" 정지 이미지가 보인다 |

10번은 처음 적어 둔 "약 1분 30초"보다 조금 늦어 표의 대기 시간을 고쳤다. 재시도 스케줄러가 10초 주기로 차례가 된 행을 맡으므로 30초, 60초 대기 뒤 최대 10초씩 더 걸리고, 측정 중 부하도 높았다. 기대 결과는 그대로 맞다.
