# Quickstart: 위험 감지와 안전장치 검증 (005-safety)

구현이 끝난 뒤 기능이 처음부터 끝까지 동작하는지 확인하는 절차다. 계약은 [contracts/safety.openapi.yaml](contracts/safety.openapi.yaml)(구현 후에는 저장소 루트 `contracts/openapi.yaml`), 데이터는 [data-model.md](data-model.md), 결정 근거는 [research.md](research.md)를 본다.

이 문서의 예시 문장은 검증용으로 지어낸 것이다. 실제 회원의 글을 옮겨 적지 않는다.

## 준비

```bash
# API: e2e 프로필은 가짜 감정 분석기와 가짜 위험 분류기를 쓴다(research R3)
cd apps/api && SPRING_PROFILES_ACTIVE=local,e2e OGU_SSE_ALLOWED_ORIGINS=http://localhost:3000 ./gradlew bootRun

# 웹
API_ORIGIN=http://localhost:8080 SSE_PUBLIC_ORIGIN=http://localhost:8080 BFF_API_KEY=local-bff-key \
  APP_ORIGIN=http://localhost:3000 pnpm --filter web dev
```

가짜 위험 분류기는 본문 머리말로 결과를 정한다.

| 머리말 | AI 분류 결과 |
|---|---|
| (없음) | 위험 없음 |
| `[우려]` | 우려 |
| `[위기]` | 위기 (키워드 목록에 없는 표현을 AI만 알아본 경우를 만든다) |
| `[위험분류실패]` | 계속 실패 |
| `[위험분류실패:2]` | 두 번 실패한 뒤 성공(위험 없음) |

**운영자 지정**(화면이 없다. research R10):

```bash
docker exec -it <postgres 컨테이너> psql -U ogu -d ogu \
  -c "update member set role = 'OPERATOR' where email = 'operator@example.com'"
```

운영자 기능은 API를 직접 부른다. `$OP`는 운영자의 access 토큰이다.

```bash
curl -s localhost:8080/api/v1/operator/assessments -H "Authorization: Bearer $OP" | jq
curl -s localhost:8080/api/v1/operator/reports -H "Authorization: Bearer $OP" | jq
curl -s -X DELETE localhost:8080/api/v1/operator/contents/POST/123/hidden -H "Authorization: Bearer $OP" -i
```

AI까지 합친 성적은 실제 키가 있어야 잰다. `AI_API_KEY`를 넣고 `local` 프로필(가짜 분류기 없이)로 띄운 뒤 `apps/api/src/test/resources/safety/eval-set.tsv`의 200문장을 글로 올려 `risk_assessment.level`을 정답과 견준다. 목표는 위기 문장을 놓치는 비율 5% 이하, 위험 없는 문장을 위기로 숨기는 비율 10% 이하다. 키가 없으면 재지 못했다고 적는다.

## 성능 측정 (SC-003, SC-004, SC-006, SC-007)

- SC-004: 글 쓰기와 댓글 쓰기를 각각 100번 불러 p95를 남긴다. 목표는 300ms 이하이고 M2의 수치(quickstart)와 견준다.
- 피드 한 쪽(글 20개, 욕설이 든 글 포함)을 100번 불러 M2의 수치와 견준다(가리기 비용).
- SC-003: 위기 표현이 든 글을 올린 응답 시각과 상세 화면에 도움 안내가 보인 시각의 차이를 20번 잰다.
- SC-006: 숨김 해제 응답 시각과 다른 회원의 피드에 그 글이 다시 나온 시각의 차이를 잰다.
- SC-007: 신고 응답 시각과 운영자 조회에 나타난 시각의 차이를 잰다.

## 운영 준비 (저장소 소유자)

1. **도움 리소스 번호를 공식 안내로 다시 확인한다.** 시드는 자살예방상담전화 109, 정신건강위기상담전화 1577-0199, 청소년상담전화 1388이다. 다르면 배포 없이 고친다.

   ```sql
   update support_resource set phone = '109', hours = '24시간' where name = '자살예방상담전화';
   ```

2. **운영자를 지정한다.** 위 "준비"의 SQL을 운영 DB에서 실행한다. 운영자는 한 명 이상이어야 한다. 아무도 없으면 잘못 숨겨진 글을 풀 사람이 없다.
3. **낱말 목록을 살핀다.** 시드의 위기, 우려, 욕설, 허용 목록을 운영자 API(`GET /api/v1/operator/terms`)로 확인하고 보탠다.
4. **운영 DB가 V4인지 확인한다.** V5는 `posts`의 부분 인덱스 셋을 다시 만든다. 지금 규모(글 수천 개)에서는 잠금 시간이 짧다.
5. **이미 있는 글 훑기.** 배포 뒤 API가 뜨면 한 번 돈다. `safety_backfill.finished_at`이 채워졌는지 확인하고, 숨겨진 글 수를 `select count(*) from posts where hidden_at is not null`로 본다. 숨겨진 글의 작성자에게는 도움 안내 알림이 간다.
6. **AI 사용량.** 글과 댓글마다 분류 호출이 한 번씩 늘어난다. 배포 뒤 며칠 동안 공급자의 사용량과 `riskClassifier` 서킷 브레이커 상태를 지켜본다.
7. **운영자의 확인 주기를 정한다.** 위기 판정과 재검토 요청은 누군가 봐야 풀린다. 알림이 가지 않으므로(스펙 Assumptions) 하루에 한 번은 `operator/assessments?reviewed=false`와 `operator/review-requests`를 본다.
8. **ADR-0005의 예외를 닫는다.** 출시일을 004 plan의 Complexity Tracking과 ADR-0005의 "결과"에 적는다.

| 글 쓰기(키워드 판정 포함, 셋에 하나는 욕설이 든 글) | 100 | 15 | 21 | 68 | p95 300 이하(SC-004) |
| 댓글 쓰기(키워드 판정 포함) | 100 | 20 | 27 | 38 | p95 300 이하(SC-004) |

M2는 글 쓰기와 댓글 쓰기의 p95를 남기지 않아 직접 견줄 수치가 없다. M2의 피드 최신순 첫 쪽은 p50 39.3ms였고(부하가 높던 때의 측정), 가리기를 더한 지금은 p50 20ms다. 가리기 비용은 측정 오차 안에 있다.

### AI까지 합친 평가 (2026-10-10)

`RiskEvalWithAiTest`로 쟀다. 서비스와 같이 키워드 규칙과 AI 분류 가운데 높은 단계를 최종 판정으로 본다. 평소에는 돌지 않고 켰을 때만 돈다.

```bash
OGU_RUN_AI_EVAL=true AI_API_KEY=... ./gradlew test --tests "*RiskEvalWithAiTest*" -i | grep EVAL
# 다른 문장 묶음, 모델, 추론 정도로 재려면
AI_EVAL_SET=/safety/eval-holdout.tsv AI_MODEL=... AI_REASONING_EFFORT=medium AI_RISK_MAX_TOKENS=1200 ...
```

**기본 모델을 바꿨다.** 앞서 기본값이던 `qwen/qwen3-next-80b-a3b-instruct`는 공급자(NVIDIA)가 2026-07-27에 서비스를 끝냈다. 호출하면 410이 온다. 그 설정으로는 감정 분석과 위험 분류가 모두 실패했다. 같은 키로 후보 17개를 불러 봤고, 답이 온 것은 `openai/gpt-oss-20b` 하나였다(나머지는 404, 시간 초과, 빈 답).

- 이 모델은 답보다 추론 과정을 먼저 내고 그 토큰도 상한에 들어간다. 위험 분류의 응답 토큰 상한을 30에서 300으로, 감정 분석을 200에서 600으로 올렸다.
- 추론 정도(`ogu.ai.reasoning-effort`)는 `low`로 둔다. 응답이 5초에서 2초로 줄었고, 형식이 틀린 응답이 7번에서 0번이 됐으며, 성적은 같았다.
- 감정 분석은 `EmotionAnalyzerLiveTest`로 확인했다. 다섯 문장 모두 기대한 감정으로 답했다(1~6초).

**프롬프트도 고쳤다.** 죽음이나 방법을 직접 말하지 않는 신호(마지막을 준비하는 행동, 수단을 마련하는 행동, 위험한 곳에 머묾, 깨어나지 않기를 바라는 말)를 위기로 보라는 지침과, 같은 낱말이 일상으로 쓰인 경우는 빼라는 지침을 더했다.

평가 문장 200개(`eval-set.tsv`)의 결과다.

**SC-005의 위기 재현율 목표(놓친 비율 5% 이하)는 채우지 못했다.** 위험 없는 문장을 위기로 숨기는 비율은 목표 안이다.

프롬프트를 이 200문장을 보며 고쳤으므로, 새로 쓴 문장 60개(`eval-holdout.tsv`)로 따로 쟀다. 위기 문장 20개는 모두 낱말 목록에 없는 에두른 표현이고, 위험 없는 문장 30개에는 같은 낱말이 일상으로 쓰인 것을 넣었다.

| 추론 정도 | 위기 문장을 위기로 | 위험 없는 문장을 위기로 | 걸린 시간 |

- 에두른 표현만 모으면 이 모델은 절반 넘게 놓친다. "가족에게 남길 편지를 다 써 놨어요", "약국을 여러 군데 돌면서 같은 약을 샀어요" 같은 문장을 위험 없음으로 본다.
- 추론 정도를 올려도 나아지지 않았다. 모델의 크기에서 오는 한계로 보인다.
- 일상 문장을 위기로 잘못 숨기는 일은 없었다.

- 위기 재현율 목표는 지금 쓸 수 있는 모델로는 채우지 못한다. 더 큰 모델을 쓸 수 있게 되면 같은 테스트로 다시 잰다.

- 공급자가 모델을 또 내릴 수 있다. 배포 뒤 `riskClassifier`, `emotionAnalyzer` 서킷 브레이커가 열려 있지 않은지 본다.
